# AGENTS.md — инструкции по установке для агента

Это руководство для автономного агента (Claude Code, CI-раннера и т.п.),
которому поручено развернуть **reflection** на сервере. Человеко-читаемое
описание проекта и конфига — в [README.md](README.md); здесь только шаги
установки/проверки и правила, которые важно не нарушить.

## Предположения

- Целевая ОС — Linux с установленным Docker и Docker Compose plugin
  (`docker compose version` должен отработать без ошибок).
- У агента есть доступ к репозиторию и, если нужно приватное зеркалирование,
  к секретам (SSH deploy-key и/или PAT-токенам целевых хостингов).
- Файлы `config.yaml`, `keys/`, `mirrors/` — в `.gitignore`; никогда не
  коммитить их и не выводить их содержимое в логи/чат, если в них есть
  реальные токены или приватные ключи.

## Шаги установки

### 1. Проверить окружение

```bash
docker compose version || { echo "docker compose не найден"; exit 1; }
```

### 2. Получить код

Если репозиторий ещё не склонирован:

```bash
git clone <URL_РЕПОЗИТОРИЯ> reflection
cd reflection
```

Если уже в рабочей директории — просто `cd` в неё и убедиться, что рабочее
дерево чистое (`git status`) перед любыми изменениями.

### 3. Создать config.yaml

```bash
[ -f config.yaml ] || cp config.example.yaml config.yaml
```

Отредактировать `config.yaml`, заполнив реальными данными секцию
`repositories`. Правила:

- Каждый репозиторий: один `source` и минимум один элемент в `destinations`
  (валидация в `config.py` упадёт с ошибкой при их отсутствии).
- Секреты (токены, пароли) **не вписывать напрямую** — использовать
  `${VAR_NAME}` и передавать значение через переменную окружения процесса
  (или `environment:` в `docker-compose.yml`). Подстановка `${VAR}` работает
  в любом строковом значении конфига.
- Если включаете `settings.webhook.enabled: true` — `settings.webhook.secret`
  обязателен (иначе процесс не стартует, `ValueError` при загрузке конфига).
  Сгенерировать токен:
  ```bash
  openssl rand -hex 32
  ```
- `settings.schedule_interval` и `repositories[].schedule_interval` — не
  меньше 60 секунд (жёсткая проверка при загрузке конфига).

### 4. Разложить SSH-ключи (если используются)

Для каждого `ssh_key: /keys/xxx` в конфиге положить соответствующий приватный
ключ локально в `./keys/xxx` и выставить права:

```bash
mkdir -p keys
chmod 600 keys/*
```

Права важны — при `0644` и более ssh-клиент откажется использовать ключ.

### 5. Задать переменные окружения

Как минимум, если вебхук включён:

```bash
export WEBHOOK_SECRET="<сгенерированный_токен>"
```

Любые другие `${VAR}`, использованные в `config.yaml` (например, токены
доступа к хостингам), также должны быть экспортированы в окружении, в котором
запускается `docker compose`, — либо положены в `.env` файл рядом с
`docker-compose.yml` (Docker Compose подхватывает `.env` автоматически).

`docker-compose.yml` уже пробрасывает в контейнер `WEBHOOK_SECRET` и
`NL_TOKEN` через `environment:` без указания значения (Compose берёт их из
окружения хоста). Если конфиг ссылается на другие имена переменных — добавить
их в список `environment:` сервиса `reflection` в `docker-compose.yml`.

### 6. Проверить конфиг перед запуском (dry-run)

Перед первым реальным запуском стоит проверить, что конфиг валиден и список
операций соответствует ожиданиям, не трогая реальные git-репозитории:

```bash
docker compose run --rm reflection --config /app/config.yaml --dry-run
```

(при первом запуске образ соберётся автоматически). Убедиться, что в выводе
перечислены все ожидаемые репозитории и destination-URL, и нет ошибок вида
`ERROR: ...` (они означают проблему в config.yaml — исправить и повторить).

### 7. Запустить сервис

```bash
docker compose up -d --build
```

### 8. Проверить, что сервис поднялся

```bash
docker compose ps
docker compose logs --tail=50 reflection
```

Если включён вебхук (порт 8080 проброшен наружу в `docker-compose.yml`):

```bash
curl -sf http://localhost:8080/health
# ожидаемо: {"status":"ok"}
```

При включённом вебхуке синхронизация всех репозиториев запускается
автоматически в фоне сразу после старта — в логах должны появиться строки
`[<repo>] fetched from source` и `[<repo>] pushed -> <url>` для каждого репо.
Если вебхук выключен, начальная синхронизация запускается синхронно при
старте процесса (тоже видна в логах) до перехода в режим ожидания по
расписанию.

Проверить ручной запуск синхронизации через вебхук (если включён):

```bash
curl -sf -X POST "http://localhost:8080/mirror?token=$WEBHOOK_SECRET"
```

Ожидаемый ответ: `{"status":"accepted","repos":"all"}`, HTTP 202.

## Обновление уже развёрнутой установки

```bash
git pull
docker compose up -d --build
```

Существующий volume `mirrors` (bare-клоны) переиспользуется — полная
пересинхронизация не требуется.

## Откат

```bash
docker compose down
git checkout <предыдущий_коммит_или_тег>
docker compose up -d --build
```

Не использовать `git reset --hard` / `docker compose down -v` без явного
запроса пользователя — `down -v` удалит volume `mirrors` и следующая
синхронизация выполнит полный `git clone --mirror` заново для всех репо.

## Частые проблемы

| Симптом                                              | Причина / решение                                                        |
|-------------------------------------------------------|---------------------------------------------------------------------------|
| `ERROR: webhook.secret must be set when webhook is enabled` | Задать `settings.webhook.secret` в конфиге (обычно через `${WEBHOOK_SECRET}`) и экспортировать переменную |
| `ERROR: Repository 'X': at least one destination required` | В `destinations` для репозитория X нет ни одного элемента |
| `ERROR: schedule_interval must be >= 60 seconds`        | Уменьшенный интервал в `settings` или в конкретном репо — увеличить до ≥60 |
| Push завершается с ошибкой аутентификации               | Проверить `ssh_key` (права 600, правильный путь внутри контейнера) либо `pat`/креды в URL |
| `401 Invalid token` на вебхуке                          | Токен в `?token=...` не совпадает с `WEBHOOK_SECRET`/`settings.webhook.secret` |
| Push отклонён хостингом (unadvertised object / hook declined) | Обычно из-за `refs/pull/*` — по умолчанию не пушится; проверить, не добавлен ли он вручную в `push_refs` |

## Что нельзя делать без явного запроса пользователя

- Коммитить `config.yaml`, содержимое `keys/`, `.env` или любые файлы с
  реальными токенами/ключами.
- Публиковать значения секретов в логах, PR-описаниях или сообщениях агенту.
- Force-push, `docker compose down -v`, удаление volume `mirrors`.
- Менять `push_refs`/refspec'и так, чтобы начать пушить `refs/pull/*` —
  большинство хостингов (Gitea/GitLab/Gitverse) отклонят это хуком.
